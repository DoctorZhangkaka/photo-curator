# 相册精选助手：产品开发与交接文档

> 文档状态：需求已确认，可据此开发
>
> 目标平台：macOS，本地单用户网页应用
>
> 默认照片根目录：`~/Desktop/相册`
>
> 本文读者：负责设计、开发、测试和后续代码审查的 Agent
>
> 重要约束：本文是需求与技术契约。开发过程中不得擅自把“移入废纸篓”改成永久删除，不得把“精选复制”改成移动，不得直接拿用户真实相册执行自动化删除测试。

---

## 1. 项目背景

用户按文件夹保存自己的摄影照片。每个一级文件夹代表一次拍摄相册，可能是：

- 一次旅行；
- 一次人像约拍；
- 后续还可能是其他拍摄主题。

照片主要来自富士和索尼相机：

- 富士 RAW：`RAF`；
- 索尼 RAW：`ARW`；
- 通用 RAW：`DNG`；
- 浏览图：`JPG` 或 `JPEG`。

同一快门产生的照片经常同时存在 RAW 和 JPG 两个文件，也可能只存在其中一种。文件可能混放，也可能已经分别放在 `RAW` 和 `JPG` 子文件夹中。

用户需要一个本地网页应用，按顺序浏览每个相册中的照片，记录浏览进度，标记精选或待删除，将待删除照片的 JPG 和对应 RAW 一起移入 macOS 废纸篓，并把精选照片复制到统一的精选目录。

后续可能加入同步，但一期不开发同步功能。一期需要避免使用会让未来同步难以实现的数据模型。

---

## 2. 产品目标

### 2.1 核心目标

1. 把同一快门产生的 RAW＋JPG 作为“一张逻辑照片”管理，避免重复浏览。
2. 支持旅行、人像约拍等任意以文件夹组织的拍摄相册，不在界面上把全部相册称为“旅游”。
3. 提供快速、稳定、适合大量照片的顺序浏览体验。
4. 独立记录“是否浏览过”和“筛选结果”。
5. 用两阶段流程删除照片，降低误删风险。
6. 一键导出精选，保持 JPG／RAW 目录结构，不改动原相册。
7. 检测 Finder 或其他程序造成的外部文件变化。
8. 对删除、恢复、导出、跳过、冲突和失败保留可追溯记录。

### 2.2 一期成功标准

用户能够分别打开一个旅行相册和一个人像约拍相册，完成以下闭环：

- 正确识别 RAW／JPG 配对和单格式照片；
- 浏览照片并自动保存已浏览状态；
- 标记精选和待删除；
- 按筛选状态及浏览状态过滤；
- 确认待删除清单并将关联文件一起移入废纸篓；
- 将精选照片复制到指定目录；
- 关闭并重启应用后状态仍在；
- 在 Finder 中新增、移动或删除文件后，应用能重新校对；
- 在操作记录中查看实际执行结果。

## 3. 非目标与一期边界

### 3.1 一期不做

- 云同步、双向同步、多设备冲突解决；
- 连拍自动分组、相似照片对比；
- AI 自动选片、模糊检测、人脸识别；
- 客户管理、订单管理、约拍交付链接；
- RAW 调色、裁剪或任何图像编辑；
- 永久删除；
- 视频、HEIC、PNG、GIF；
- XMP 编辑或随 RAW 自动处理 XMP；
- 多用户、登录、公网访问；
- 自动把精选结果反向同步回原相册；
- 自动清理已经导出的精选副本。

### 3.2 目录边界

- 只把照片根目录下的一级子文件夹识别为相册。
- `精选原相册` 是导出目录，必须排除，不得作为源相册导入。
- 排除隐藏目录、应用数据目录和符号链接目录。
- 每个相册支持：
  1. 图片直接放在相册根目录；
  2. 图片放在相册下的 `RAW` 和 `JPG` 子目录；
  3. 同一个相册中上述两种结构同时存在。
- `RAW`、`JPG` 目录名称不区分大小写。
- 不递归扫描除上述两个一级子目录之外的更深目录。发现其他嵌套目录中的受支持图片时，可在扫描报告中提示“未纳入”，但不得擅自纳入。
- 根目录下直接存在的图片不属于任何相册，一期忽略并可在扫描报告中提示。

### 3.3 文件边界

一期仅处理以下扩展名，匹配时不区分大小写：

- 浏览图：`.jpg`、`.jpeg`；
- RAW：`.raf`、`.arw`、`.dng`。

源文件读取、扫描和导出必须限制在已配置的照片根目录内，导出也位于该根目录内的固定精选目录。唯一的路径范围例外是：调用 macOS 原生废纸篓 API 时，文件会进入系统废纸篓；后续恢复只能使用该 API 返回并持久化的实际废纸篓位置，且恢复目标仍必须是根目录内的原路径。不得把这一例外扩展为任意路径读写能力，也不得通过符号链接、路径穿越或 API 传入任意绝对路径访问其他根目录之外的文件。

## 4. 核心概念与状态模型

### 4.1 术语

| 术语 | 定义 |
| --- | --- |
| 相册 | 照片根目录下的一个一级文件夹，可代表旅行、人像约拍或其他拍摄主题 |
| 逻辑照片 | 用户在界面上看到的一张照片，可包含一个 JPG、一个 RAW，或一个 JPG＋一个 RAW |
| 文件资产 | 磁盘上的实际 JPG、RAF、ARW 或 DNG 文件 |
| 配对 | 按同一相册内的规范化主文件名，把 JPG 与 RAW 关联为一张逻辑照片 |
| 浏览状态 | 未浏览或已浏览，与筛选结果无关 |
| 筛选状态 | 未筛选、精选或待删除，三者互斥 |
| 文件缺失 | 数据库中仍有记录，但外部扫描发现对应文件已不在原位置 |
| 配对冲突 | 同名候选关系不符合安全配对规则，系统禁止自动执行删除或导出 |
| 清理 | 将待删除逻辑照片的实际文件移入 macOS 废纸篓 |
| 导出精选 | 将精选逻辑照片的实际文件复制到固定精选目录 |

### 4.2 两个独立状态维度

不得把状态简单设计成一个包含四种值的字段。

#### 浏览状态

- `unseen`：未浏览；
- `viewed`：已浏览。

规则：

- 逻辑照片的大图成功展示后，自动变为已浏览；
- 仅在胶片栏中渲染缩略图不算已浏览；
- 用户可手动将照片改回未浏览；
- 浏览状态按相册持久化，重启后保留。

#### 筛选状态

- `unmarked`：未筛选；
- `selected`：精选；
- `pending_delete`：待删除。

规则：

- 三种状态互斥；
- 从未筛选切换到精选：直接切换；
- 从精选切换到待删除：取消精选并进入待删除；
- 从待删除切回精选：取消待删除并进入精选；
- 取消精选或取消待删除后进入未筛选，不自动恢复更早的状态；
- 状态变更不改动图片文件，不写入 EXIF 或 XMP。

### 4.3 过滤条件

以下过滤条件可组合：

- 浏览：全部／未浏览／已浏览；
- 筛选：全部／未筛选／精选／待删除；
- 文件形态：全部／JPG＋RAW／仅 JPG／仅 RAW；
- 异常：配对冲突／文件缺失／导出冲突。

默认显示“全部浏览状态＋全部非待删除筛选状态”还是“全部照片”，开发时采用以下明确规则：

- 默认显示全部照片，包括待删除；
- 待删除照片保留明显视觉标识；
- 清理完成后，已移入废纸篓的照片从当前相册正常列表移除；
- 文件缺失不是待删除，必须单独显示。

## 5. 用户体验与界面设计

## 5.1 信息架构

一期包含四个主要视图：

1. **相册库**：浏览和选择相册；
2. **照片筛选器**：核心浏览、标记、过滤、清理和导出；
3. **操作记录**：查看删除、恢复、导出及失败明细；
4. **异常中心**：查看配对冲突、文件缺失和导出冲突。

应用使用中文界面。文案统一使用“相册”或“拍摄相册”，不要把人像约拍相册称为“旅行”。

## 5.2 相册库

每个相册卡片至少显示：

- 相册名称，即原文件夹名称；
- 封面：第一张可展示照片的缩略图；
- 逻辑照片总数；
- 已浏览／总数；
- 精选数量；
- 待删除数量；
- 文件缺失或配对冲突数量；
- 最后扫描时间。

支持：

- 按名称或最近打开时间排序；
- 手动“重新扫描全部相册”；
- 打开相册时自动重新扫描该相册；
- 显示扫描中、扫描失败、空相册状态；
- 不显示 `精选原相册`。

相册类型不需要用户额外选择。旅行和人像约拍只是使用场景，一期不强制增加分类字段。

## 5.3 照片筛选器布局

桌面端建议布局：

- 顶栏：返回相册库、相册名称、排序、过滤器、扫描状态；
- 主区域：大图查看器；
- 底部：虚拟化缩略图胶片栏；
- 右侧可折叠面板：照片信息、状态、文件清单、EXIF；
- 底部或顶栏操作区：精选、待删除、清理待删除、导出精选。

大图区域至少显示：

- 当前位置，例如 `126 / 480`；
- 已浏览／未浏览；
- 精选／未筛选／待删除；
- JPG＋RAW／仅 JPG／仅 RAW；
- 配对冲突、文件缺失等异常标记；
- 当前主文件名；
- 加载失败和重试状态。

### 5.4 浏览操作

- 上一张／下一张按钮；
- 键盘左右方向键；
- 点击胶片栏跳转；
- 全屏；
- 放大、缩小、适应屏幕、100% 查看和拖动；
- 自动播放与暂停；
- 自动播放间隔默认 3 秒，可选 2、3、5、10 秒；
- 自动播放到达末尾后停止，不默认循环；
- 用户执行精选、待删除、清理或导出操作时暂停自动播放，避免误操作；
- 预加载当前照片前后各至少 2 张；
- 切换排序后保留当前逻辑照片，不应无故跳回第一张。

### 5.5 默认快捷键

| 按键 | 行为 |
| --- | --- |
| `←` | 上一张 |
| `→` | 下一张 |
| `F` | 精选／取消精选 |
| `X` 或 `Delete` | 标记待删除／取消待删除 |
| `Space` | 播放／暂停自动浏览 |
| `I` | 显示／隐藏照片信息 |
| `U` | 切换已浏览／未浏览 |
| `Esc` | 关闭弹窗或退出全屏 |

约束：

- 输入框、文本域或可编辑元素聚焦时，不触发上述快捷键；
- `Delete` 只改变待删除状态，不得直接移动文件；
- 不把浏览器保留快捷键作为唯一操作入口；
- 所有快捷键都有对应的可点击按钮。

### 5.6 清理待删除流程

采用严格的两阶段流程。

#### 阶段 A：标记

- 用户按 `X`、`Delete` 或点击按钮，只更新筛选状态；
- 原文件保持不动；
- 可逐张或批量取消待删除；
- 待删除照片不能再作为精选导出。

#### 阶段 B：预检

用户点击“清理待删除”后，后端重新扫描并生成预检结果：

- 待删除逻辑照片数量；
- 实际将移动的文件数量；
- 每个逻辑照片的 JPG／RAW 文件相对路径；
- 文件缺失、配对冲突、状态已变化等阻止项；
- 预计释放空间，可按实际文件大小求和；
- 明确提示“文件将移入 macOS 废纸篓，不会永久删除”。

如果存在阻止项：

- 默认整批不执行；
- 用户可以返回处理异常后重新预检；
- 一期不提供“忽略异常并删除其余文件”的隐式选项，避免用户误以为异常照片也已处理。

#### 阶段 C：确认与执行

- 用户明确确认后才执行；
- 预检结果具有短期有效令牌和文件指纹；
- 执行前再次校验文件路径、大小、修改时间和配对关系；
- 任一文件在执行前发生变化，停止该批次并返回 `409 CONFLICT`，要求重新预检；
- 每张逻辑照片的 JPG 和 RAW 必须作为一个操作组；
- 如果同组任一文件移动失败，尽可能把该组已经移动的文件恢复到原路径；
- 回滚也失败时，显示严重错误并写入操作记录，不得报告为成功；
- 清理完成后显示成功组数、文件数、失败数和撤销入口。

#### 撤销

- 清理完成后提供一次短时撤销入口，建议界面保留 15 秒，同时在操作详情中保留“尝试恢复”能力；
- 只有原生废纸篓 API 返回的实际废纸篓位置可用于恢复；
- 恢复前检查原路径是否已有新文件；存在冲突时不得覆盖；
- 撤销失败时明确提示用户可在 Finder 废纸篓手动恢复；
- 恢复结果必须写入操作记录。

### 5.7 精选导出流程

点击“导出精选”后：

1. 后端重新扫描当前相册；
2. 仅选择筛选状态为 `selected` 的逻辑照片；
3. 排除待删除、未筛选、配对冲突和文件缺失项目；
4. 展示待导出照片数、JPG 数、RAW 数、总字节数；
5. 明确展示目标目录；
6. 用户确认后复制；
7. 显示进度和最终结果。

目标结构固定为：

```text
~/Desktop/相册/精选原相册/
└── 原相册文件夹名称/
    ├── JPG/
    └── RAW/
```

规则：

- 每次导出都创建 `JPG` 和 `RAW` 两个目录，即使其中一个为空；
- 复制，不移动；
- 保留原文件名、扩展名大小写和文件内容；
- 不重新压缩 JPG，不转换 RAW，不重写 EXIF；
- 导出后原精选状态保留；
- 重复导出是增量操作；
- 目标存在同名同内容文件时记录为“已存在，跳过”；
- 目标存在同名不同内容文件时记录为“冲突，未覆盖”；
- 不自动添加 `(1)`、时间戳或其他后缀；
- 取消精选不会删除此前已经导出的文件；
- 如果当前没有可导出的精选照片，按钮禁用或展示明确空状态；
- 导出过程中源文件发生变化时，该项目失败并记录，不得假装完成。

### 5.8 操作记录

列表至少支持按相册、操作类型、状态和时间过滤。

每条操作显示：

- 操作类型：清理、撤销恢复、导出、扫描；
- 开始和结束时间；
- 状态：预检、执行中、成功、部分失败、失败、已恢复；
- 相册名称；
- 逻辑照片数和文件数；
- 操作明细；
- 错误信息。

单个文件明细包括：

- 原相对路径；
- 目标相对路径或废纸篓返回位置；
- 文件大小；
- 结果：成功、跳过、冲突、失败、恢复；
- 失败原因；
- 内容哈希（已计算时）。

操作记录保存在应用本地数据库，不写进源相册，不自动清除。提供查看和筛选即可，一期不要求提供“清空记录”。

### 5.9 异常中心

至少区分：

- 配对冲突；
- 文件缺失；
- 导出同名不同内容冲突；
- RAW 预览生成失败；
- 扫描权限或读取错误。

一期解决配对冲突的推荐交互是：

- 显示相关文件的完整相对路径；
- 提供“在 Finder 中显示”；
- 用户在 Finder 中重命名或整理后点击“重新扫描”；
- 在冲突未解除前，不自动删除或导出该逻辑组。

不要求一期开发任意拖拽配对编辑器。

## 6. 排序与元数据规则

### 6.1 默认排序

默认按拍摄时间升序：

1. 优先读取 EXIF `DateTimeOriginal`；
2. 其次可使用 `CreateDate`；
3. 无法读取时使用自然文件名排序；
4. 同一拍摄时间或无法确定时间时，以规范化主文件名自然排序；
5. 最后以逻辑照片 ID 作为稳定次序，避免刷新后随机跳动。

可切换为文件名自然排序。自然排序应让 `2`、`10` 的顺序符合数字直觉，而不是简单字符串顺序。

### 6.2 配对照片的元数据

- 有 JPG 时优先读取 JPG 的 EXIF；
- 仅 RAW 时读取 RAW 元数据；
- 配对文件时间明显不一致时，不据此自动拆散同名配对；
- 元数据只用于展示和稳定排序，不覆盖基于文件名的配对约束。

### 6.3 展示字段

能读取时展示：

- 拍摄时间；
- 相机品牌与型号；
- 镜头型号；
- 焦距；
- 光圈；
- 快门速度；
- ISO；
- 图像宽高；
- 文件大小；
- 实际包含的文件格式。

读取失败不阻止浏览，只显示“未知”。

## 7. RAW／JPG 配对算法

### 7.1 基本原则

- 配对范围仅限同一相册；
- 不跨相册配对；
- 不根据图像相似度配对；
- 不仅凭拍摄时间配对；
- 不把多个同格式文件静默合并成一组。

### 7.2 规范化

对每个受支持文件：

1. 扩展名转小写，用于类型判断；
2. 去掉最后一个扩展名，得到主文件名；
3. 主文件名做 Unicode NFC 规范化；
4. 配对比较使用不区分大小写的规范化主文件名；
5. 数据库存储原始文件名和原始相对路径，展示时不得改成小写。

示例：

```text
DSCF0001.JPG + DSCF0001.RAF       => 一组
DSCF0001.jpeg + raf/DSCF0001.RAF  => 一组
_DSC1234.JPG + ARW/_DSC1234.ARW   => 一组
DSCF0002.JPG                      => 仅 JPG
DSCF0003.RAF                      => 仅 RAW
```

`RAW` 和 `JPG` 子目录名称不区分大小写，目录名本身不进入配对键。

### 7.3 正常组

一个正常逻辑照片只能是以下三种之一：

- 一个 JPG／JPEG；
- 一个 RAW；
- 一个 JPG／JPEG＋一个 RAW。

### 7.4 冲突组

以下情况必须标记冲突，不得自行猜测：

- 同一规范化主文件名对应两个或更多 JPG／JPEG；
- 同一规范化主文件名对应两个或更多 RAW；
- 同时存在 RAF、ARW、DNG 等多个 RAW 候选；
- 因大小写或 Unicode 规范化导致不同原始文件落入同一个配对键；
- 文件在预检和执行之间改变，导致配对关系变化。

冲突组可以在异常中心展示文件，但不得作为正常照片执行清理或导出。浏览时可提供只读文件列表；若能够明确生成单文件预览，可预览，但不能因此解除冲突。

### 7.5 扫描与状态合并

- 相册身份使用 UUID，并保存相对于照片根目录的相册路径；
- 逻辑照片使用 UUID，并保存 `album_id + normalized_pair_key` 唯一约束；
- 文件资产使用 UUID，并保存相对于相册根目录的路径；
- 重新扫描时优先按上述稳定键合并已有状态；
- 用户在外部重命名主文件后，可视为新逻辑照片；一期不保证保留原筛选状态；
- 文件暂时缺失时不立即删除数据库状态，标记缺失；
- 文件重新出现在相同位置时恢复正常展示并合并原状态；
- 应用自身完成清理后，将其记录为已清理，不应被下一次扫描误报成“外部缺失”。

## 8. 技术方案

## 8.1 推荐架构

采用“本地后端＋网页前端”：

- 前端：React、TypeScript、Vite；
- 样式：Tailwind CSS，组件风格保持克制，以照片为视觉中心；
- 数据请求：TanStack Query 或等效方案；
- 后端：Python、FastAPI、Uvicorn；
- 数据库：SQLite，开启 WAL 和外键；
- ORM／迁移：SQLAlchemy＋Alembic，或具有同等迁移能力的方案；
- 文件监听：watchdog；
- JPG 缩略图：Pillow；
- RAW 解码：rawpy／LibRaw；
- EXIF：ExifTool 为首选，统一支持富士、索尼和 JPG；缺少依赖时给出健康检查提示；
- macOS 废纸篓：优先 PyObjC 调用 `NSFileManager trashItemAtURL:resultingItemURL:error:`，以获得实际废纸篓位置；
- 实时事件：SSE，或等效的本机推送机制；
- 测试：Pytest、Vitest、React Testing Library、Playwright。

技术选型可以替换，但必须保留本文的文件安全、状态模型、配对规则、操作日志和测试要求。

### 8.2 为什么不是纯前端

浏览器沙箱无法可靠完成：

- 对任意本地相册目录持续扫描；
- RAF／ARW 本地解码；
- 将文件原生移入 macOS 废纸篓并追踪返回位置；
- 原子复制、冲突检测和详细文件日志；
- 文件系统监听。

因此不能把一期实现成只有一个静态 HTML 或纯浏览器 IndexedDB 的方案。

### 8.3 进程与端口

- 后端默认仅监听 `127.0.0.1`；
- 前端开发服务器默认仅监听 `127.0.0.1`；
- 不得默认绑定 `0.0.0.0`；
- 根目录 `npm run dev` 同时启动前后端；
- 根命令必须把 CLI 的 host／port 参数转发给 Vite；
- 默认逻辑预览端口为 `7100`，本地 API 端口可默认 `8765`；
- 开发环境通过 Vite 同源代理访问 API；
- 生产模式可由后端托管前端构建产物，保持同源。

### 8.4 安全要求

- API 不接受任意文件绝对路径作为操作目标；优先使用相册 ID、逻辑照片 ID 和预检令牌；
- 所有路径由后端从数据库记录和受控根目录构造；
- 使用路径解析与真实路径校验，阻止 `..`、符号链接逃逸和根目录外操作；
- 不拼接 shell 字符串执行文件命令；外部工具使用参数数组；
- 写操作要求同源，并加入本地会话令牌或 CSRF 防护；
- CORS 默认关闭，只允许明确的本地开发来源；
- 不将源照片、预览或日志上传到第三方服务；
- 除明确检查依赖更新外，一期运行不需要外网；
- 前端 XSS 防护不得依赖手动拼接 `innerHTML`；
- 日志不得记录本地会话令牌。

## 9. 数据模型建议

以下为逻辑模型，字段可按 ORM 调整，但语义不得丢失。

### 9.1 `settings`

- `key`：主键；
- `value`：配置值；
- `updated_at`。

至少保存：

- 照片根目录；
- 精选目录名称，默认 `精选原相册`；
- 默认排序；
- 自动播放间隔；
- 数据库模式版本。

### 9.2 `albums`

- `id`：UUID；
- `relative_path`：相对于照片根目录，唯一；
- `name`：原始文件夹名称；
- `cover_photo_id`：可空；
- `last_opened_at`；
- `last_scanned_at`；
- `scan_status`；
- `created_at`；
- `updated_at`；
- `deleted_at`：为未来同步预留，可空。

### 9.3 `photo_groups`

- `id`：UUID；
- `album_id`：外键；
- `normalized_pair_key`；
- `display_name`；
- `viewed_status`：`unseen`／`viewed`；
- `selection_status`：`unmarked`／`selected`／`pending_delete`；
- `pairing_status`：`normal`／`conflict`／`missing`／`trashed`；
- `capture_time`：可空；
- `sort_key`；
- `version`：乐观锁版本号；
- `created_at`；
- `updated_at`；
- `deleted_at`：可空。

唯一约束：`(album_id, normalized_pair_key)`。若冲突组合并策略需要额外组，可增加冲突子键，但不得让正常配对产生重复逻辑照片。

### 9.4 `assets`

- `id`：UUID；
- `photo_group_id`：外键；
- `kind`：`jpg`／`raw`；
- `extension`：原始扩展名；
- `relative_path`：相对于相册根目录；
- `original_filename`；
- `size_bytes`；
- `mtime_ns`；
- `presence_status`：`present`／`missing`；
- `content_sha256`：可空，需要时计算；
- `preview_status`；
- `created_at`；
- `updated_at`。

唯一约束建议为 `(photo_group_id, relative_path)`。扫描时同时需要按相册和相对路径定位资产。

### 9.5 `operations`

- `id`：UUID；
- `idempotency_key`：唯一，防止重复执行；
- `album_id`：可空；
- `type`：`scan`／`cleanup`／`restore`／`export`；
- `status`；
- `requested_at`；
- `started_at`；
- `finished_at`；
- `requested_photo_count`；
- `requested_file_count`；
- `success_file_count`；
- `skipped_file_count`；
- `failed_file_count`；
- `error_summary`；
- `request_snapshot_json`；
- `created_at`。

操作记录采用追加式语义。状态字段可以随任务生命周期更新，但完成后的明细不得被后续无关扫描覆盖。

### 9.6 `operation_items`

- `id`：UUID；
- `operation_id`：外键；
- `photo_group_id`：可空但保留原显示名快照；
- `asset_id`：可空但保留原路径快照；
- `source_relative_path`；
- `destination_path_snapshot`；
- `source_size_bytes`；
- `source_mtime_ns`；
- `content_sha256`：可空；
- `result`；
- `error_code`；
- `error_message`；
- `created_at`。

### 9.7 `export_conflicts`

可单独建表，也可由操作明细和当前异常投影生成。至少要能持续展示：

- 相册；
- 源文件；
- 目标文件；
- 冲突类型；
- 最近发现时间；
- 对应操作 ID。

### 9.8 数据库要求

- 开启 `foreign_keys=ON`；
- 开启 WAL；
- 所有状态变更使用事务；
- 文件系统不能与 SQLite 组成真正事务，必须用操作日志记录执行阶段；
- 启动时检查 `executing` 等中断操作并标记为“中断，需核对”，不得直接当作成功；
-  schema 变更必须有迁移，不允许靠删除数据库升级。

## 10. API 契约建议

所有响应使用统一错误结构。路径仅作建议，开发 Agent 可微调，但功能必须完整。

### 10.1 健康与配置

#### `GET /api/health`

返回：

- 后端状态；
- 数据库是否可用；
- 照片根目录是否存在、可读写；
- 精选目录是否可创建；
- ExifTool、LibRaw／rawpy、macOS 废纸篓能力是否可用；
- 当前版本。

#### `GET /api/config`

返回非敏感配置：根目录、精选目录名、支持格式、功能状态。

一期可以固定根目录，但测试必须能通过环境变量指向临时目录。

### 10.2 相册与扫描

- `GET /api/albums`：相册及统计；
- `POST /api/albums/rescan`：全量校对；
- `GET /api/albums/{albumId}`：详情；
- `POST /api/albums/{albumId}/rescan`：扫描指定相册；
- `GET /api/albums/{albumId}/events`：文件变化和任务事件，可选 SSE。

### 10.3 逻辑照片

#### `GET /api/albums/{albumId}/photos`

支持：

- 游标分页；
- 浏览状态过滤；
- 筛选状态过滤；
- 文件形态过滤；
- 异常过滤；
- 拍摄时间／文件名排序。

响应包含稳定游标和总数，不把十万级数据一次性返回前端。

#### `GET /api/photos/{photoId}`

返回：

- 两个独立状态；
- 配对状态；
- 文件资产清单；
- EXIF；
- 排序字段；
- 当前版本号。

#### `PATCH /api/photos/{photoId}/state`

请求示例：

```json
{
  "viewedStatus": "viewed",
  "selectionStatus": "selected",
  "version": 12
}
```

允许只更新一个维度。版本不一致返回 `409`，前端刷新后重试，不能静默覆盖新状态。

#### 媒体端点

- `GET /api/photos/{photoId}/thumbnail`；
- `GET /api/photos/{photoId}/preview`；
- `GET /api/photos/{photoId}/original-preview`：用于高质量缩放，可返回原 JPG 或 RAW 解码预览。

要求：

- 设置合适缓存头；
- 文件指纹变化后缓存失效；
- 不暴露任意路径读取能力；
- 对缺失、冲突和解码失败返回明确错误。

### 10.4 清理与恢复

#### `POST /api/albums/{albumId}/cleanup/preflight`

返回：

- 预检令牌；
- 过期时间；
- 待处理逻辑照片和文件快照；
- 阻止项；
- 总字节数。

#### `POST /api/albums/{albumId}/cleanup/execute`

请求包含：

- 预检令牌；
- 幂等键。

执行前重新验证。重复提交相同幂等键不得重复移动文件，应返回原操作状态。

#### `POST /api/operations/{operationId}/restore`

恢复指定清理操作。存在目标冲突时不得覆盖，返回逐项结果。

### 10.5 精选导出

- `POST /api/albums/{albumId}/exports/preflight`；
- `POST /api/albums/{albumId}/exports`；
- `GET /api/jobs/{jobId}`；
- `GET /api/operations/{operationId}`。

导出执行使用幂等键，返回任务 ID。前端断线重连后可继续查询任务，不得因重复点击产生多个相同导出任务。

### 10.6 操作与异常

- `GET /api/operations`；
- `GET /api/operations/{operationId}`；
- `GET /api/albums/{albumId}/issues`；
- `POST /api/albums/{albumId}/issues/rescan`；
- `POST /api/assets/{assetId}/reveal-in-finder`：只能揭示数据库中已登记且通过路径校验的资产。

### 10.7 标准错误码建议

- `ALBUM_NOT_FOUND`；
- `PHOTO_NOT_FOUND`；
- `STALE_VERSION`；
- `PREFLIGHT_EXPIRED`；
- `SOURCE_CHANGED`；
- `PAIRING_CONFLICT`；
- `ASSET_MISSING`；
- `DESTINATION_CONFLICT`；
- `PATH_OUTSIDE_ROOT`；
- `TRASH_OPERATION_FAILED`；
- `ROLLBACK_FAILED`；
- `RAW_PREVIEW_UNAVAILABLE`；
- `DEPENDENCY_UNAVAILABLE`。

错误响应应包含可展示给用户的中文摘要和可供排查的技术细节，但不得泄露会话令牌。

## 11. 扫描、监听与缓存

### 11.1 扫描触发

- 应用启动；
- 打开相册；
- 用户手动刷新；
- 当前相册文件系统事件触发；
- 清理或导出前的强制预检扫描。

### 11.2 文件监听

- 监听当前打开相册即可，不必始终监听整个照片库；
- 事件去抖建议 500–1000 毫秒；
- 文件复制过程可能产生连续事件，需等文件稳定后再更新预览；
- 监听事件只是提示，最终以完整校对扫描为准；
- 应用退出期间的变更，在下次启动扫描时处理；
- 扫描发现文件缺失时保留状态并标记，不立即清除记录；
- 外部恢复文件后，下一次扫描应消除缺失状态。

### 11.3 浏览和导出期间的变化

- 当前照片资产消失时，大图显示“文件已变化”，禁用清理和导出；
- 后台扫描完成后刷新列表，并尽量保留当前逻辑照片；
- 状态更新遇到版本冲突时提示，不静默覆盖；
- 清理和导出预检后任何源文件变化都会使预检失效。

### 11.4 预览缓存

缓存必须放在应用数据目录，不得放入源相册。

建议：

- 缩略图长边约 512 px；
- 普通预览长边约 2560 px；
- JPG 优先直接生成缓存；
- RAW-only 使用 rawpy／LibRaw 解码生成预览；
- 缓存键至少包含文件相对路径、大小、修改时间和预览规格；
- 文件变化后生成新缓存，旧缓存可异步清理；
- 缓存失败不得改动原文件；
- 同一文件的预览生成需要去重，避免并发解码耗尽内存；
- 限制 RAW 解码并发数，建议默认为 1 或 2。

## 12. 文件操作安全设计

### 12.1 通用约束

任何清理、恢复、导出操作前：

1. 根据 ID 获取数据库快照；
2. 验证解析后的真实路径处于允许根目录；
3. 检查路径中没有用于逃逸的符号链接；
4. 检查文件类型和扩展名；
5. 检查文件存在且为普通文件；
6. 校验大小和修改时间；
7. 记录操作明细；
8. 执行后再次核对结果。

不得仅凭前端提交的路径或配对关系执行文件操作。

### 12.2 清理分组与回滚

每张逻辑照片是一个操作组：

- 仅 JPG：移动一个文件；
- 仅 RAW：移动一个文件；
- JPG＋RAW：两个文件都成功才算成功；
- 配对冲突或缺失：整组不执行。

若双文件组第一步成功、第二步失败：

1. 尝试把第一个文件从原生 API 返回的废纸篓位置移回；
2. 原路径已经存在新文件时不得覆盖；
3. 记录回滚结果；
4. 回滚失败时把操作标为严重失败，并向用户展示两个实际位置。

不能仅依靠固定的 `~/.Trash/文件名` 猜测废纸篓位置，因为 Finder 可能重命名冲突项目。

### 12.3 导出复制

- 在目标目录内先写临时文件；
- 复制完成后检查字节数，必要时计算 SHA-256；
- 目标已存在时先比较内容；
- 同内容：删除临时文件，记录跳过；
- 不同内容：不覆盖，记录冲突；
- 目标不存在时以不允许覆盖的方式发布最终文件；
- 发布成功后删除临时文件；
- 应用崩溃后可在下次启动时清理属于本应用的过期临时文件；
- 不修改源文件权限、时间戳或扩展属性；复制工具不得主动改写内容。

### 12.4 备份提示

首次进入清理功能时显示一次说明：

- 本应用移入废纸篓，不是永久删除；
- 重要照片仍建议保留独立备份；
- 清空 macOS 废纸篓后，本应用无法保证恢复。

不要求每次弹窗都展示长篇说明，但清理确认框必须保留核心提示。

## 13. 性能与可用性目标

以下是合理目标，不应通过牺牲安全性达成：

- 1000 张逻辑照片的相册，已有缓存时打开后先显示列表和已有缩略图，不等待所有 EXIF／RAW 解码完成；
- 缩略图胶片栏虚拟化，不一次挂载全部图片节点；
- 已缓存预览的上一张／下一张切换应接近即时；
- 未缓存 JPG 在普通本地 SSD 上目标 1 秒内可显示；
- RAW-only 解码可以较慢，但必须显示进度，不阻塞整个界面；
- 扫描和导出在后台执行，界面可查看进度；
- 大型导出使用流式复制，不把整个文件读入内存；
- 限制并发 RAW 解码和哈希任务，避免系统失去响应；
- 状态更新先持久化，再依赖界面刷新，重启不能丢状态。

建议开发 Agent 构造一个至少 1000 张逻辑照片的性能测试相册，可用小尺寸测试 JPG 和重复生成文件，不使用用户私人照片。

## 14. 可访问性与视觉要求

- 照片是视觉中心，查看器使用深色或中性背景；
- 精选、待删除不能只靠颜色表达，同时提供图标和文字；
- 所有按钮有可读标签或辅助说明；
- 键盘焦点清晰；
- 弹窗支持 Esc 和焦点约束；
- 错误信息可读且包含下一步；
- 缩略图有文件名替代文本；
- 200% 界面缩放时核心操作仍可用；
- 窗口较小时右侧面板可折叠，胶片栏不能挤没大图；
- 不要求一期完整支持手机触屏，但布局不得假定只有一个固定分辨率。

## 15. 测试策略

### 15.1 测试环境硬约束

- 自动化测试不得使用 `~/Desktop/相册` 真实目录；

## 21. 后续代码审查清单

用户后续会把代码仓库交给另一个 Agent 检查。审查时至少核对：

### 21.1 需求一致性

- 旅行和人像约拍都只是一级目录相册；
- 浏览状态与筛选状态是两个维度；
- `Delete` 只标记待删除；
- 清理是两阶段且只进废纸篓；
- 精选是复制而非移动；
- 精选目录被排除；
- 连拍、相似照片和同步没有提前混入一期。

### 21.3 正确性与体验

## 22. 已确认决策汇总

为避免开发 Agent 从上下文猜测，以下决策视为已经确认：

1. 相册同时覆盖旅游和人像约拍，使用通用“相册”概念。
2. 浏览状态为“未浏览／已浏览”。
3. 筛选状态为“未筛选／精选／待删除”。
4. 两个状态维度独立持久化。
5. `X` 或 `Delete` 只标记待删除。
6. 只有“清理待删除”确认后才移入 macOS 废纸篓。
7. 不做永久删除。
8. JPG 与 RAW 配对清理；单格式正常处理。
9. 配对冲突禁止自动清理和导出。
10. 默认拍摄时间升序，可切换文件名排序。
11. 精选导出采用复制，原相册不变。
12. 固定导出到 `精选原相册/原相册名称/JPG|RAW`。
13. 重复导出增量跳过，同名不同内容不覆盖。
14. 取消精选不删除历史导出副本。
15. 实现外部变化检测和下次启动校对。
16. 实现删除、恢复、导出、跳过和失败操作记录。
17. 一期不做连拍与相似照片对比。
18. 一期不做同步，但保留 UUID、时间戳和删除标记等扩展空间。
19. 一期不处理视频、HEIC、PNG、XMP 和复杂嵌套目录。
20. 所有开发与自动化测试使用测试副本或临时夹具，不直接对真实照片执行删除测试。
